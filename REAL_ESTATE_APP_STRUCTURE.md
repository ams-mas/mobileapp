# Real Estate Management Android App — Structure

This repository is the Android client for the Afghanistan real estate management system.

## Technology
- Kotlin and Jetpack Compose for the Android interface.
- MVVM-style feature screens and ViewModels.
- Repository pattern to separate UI from data access.
- HTTPS REST API to the existing PHP backend; the app must never connect directly to MySQL.
- Firebase Cloud Messaging (FCM) for push notifications, with SMS sent by the PHP backend through a provider integration.
- Persian/Dari, Pashto, and English localization; support right-to-left layouts.

## Main app options
### Staff / agents
1. Sign in and role-based access.
2. Dashboard: property totals, available properties, inquiries, appointments, and recent activity.
3. Properties: browse, search, filter, view details/photos/map, create and edit records according to permissions. Property codes are generated by the server and read-only in the app.
4. Customers / buyers: contact details, budget, preferred locations and property types.
5. Inquiries and follow-ups: record customer interest and next actions.
6. Appointments: schedule property visits and view upcoming visits.
7. Contracts and transaction records: view or manage records according to permissions. Prices and contract amounts are records only; no online payment processing.
8. Notifications: property alerts and system updates.
9. Messages: select recipients, preview messages, send requests to the backend, and view delivery history. SMS recipients must be selected deliberately; support Afghan +93 numbers and opt-out preferences.
10. Reports: summaries available to the signed-in role.
11. Settings: language, profile, notification preferences, and sign out.

### Buyer-facing access (optional, based on business policy)
- Browse published properties.
- Search and filter listings.
- Save favorites and submit inquiries.
- Receive opted-in push/SMS notifications.
- Contact the agency.

## Folder guide
- `core/`: shared navigation, networking, security helpers, notifications, and theme.
- `data/local/`: local preferences/cache only; never store secrets.
- `data/remote/`: API service definitions and request/response DTOs.
- `data/repository/`: implementations that coordinate remote/local data.
- `domain/model/`: app business models.
- `domain/repository/`: repository interfaces.
- `domain/usecase/`: business actions shared by screens.
- `feature/`: screens and ViewModels grouped by feature.
- `res/`: Android resources and localized strings.

## Security and integration rules
- Never embed database credentials or SMS-provider keys in the Android app.
- Authenticate against a server API; enforce permissions and validation on the PHP backend.
- Use HTTPS, short-lived/rotatable tokens where supported, and safe token storage.
- Keep SMS credentials and message sending on the server; log delivery status without exposing secrets.
- Ask for notification/SMS consent and respect opt-outs.
- Do not implement online payments.
- Do not trust a property code supplied by the app; the server generates it.

## Implementation order
1. Confirm the existing PHP backend API and authentication format.
2. Build navigation, localization, and sign-in.
3. Add property listing/detail screens using API models.
4. Add customers, inquiries, and appointments.
5. Add role-aware contracts/records and dashboard.
6. Add FCM and backend-driven SMS workflows.
7. Add tests, error/loading/empty states, and release configuration.

This document describes the planned architecture. Empty feature folders are scaffolding; features are not implemented merely because their folders exist.
